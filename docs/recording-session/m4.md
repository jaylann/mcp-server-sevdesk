# M4 runs

The M4 part of the [recording session](../recording-session.md): receipts, reconciliation, exports
and e-invoices, about 30 minutes. Run it on the same trial account after
[step 3](../recording-session.md#3-run-the-session-about-20-minutes). The M4 probes
(`m4-*-probes.ts`) and the M4 lifecycle scenario need a little more preparation.

## What to prepare

1. **Company data** (Einstellungen → Unternehmen): street, zip, city, IBAN and BIC, contact
   e-mail and phone, Steuernummer or USt-IdNr. sevDesk needs them to finalize an e-invoice; the
   probe `write-einvoice-xml` names the empty `GET /SevClient` fields when `sendBy` refuses. Fake
   values are fine (Musterfirma, a test IBAN such as `DE02120300000000202051`).
2. **DATEV export configuration** (accountant number, client number, start of the fiscal year).
   Without it sevDesk refuses the export job. Either enter fake values in the web app (DATEV
   settings) or let the opt-in probe `write-export-datev-config` set accountant 1001, client 1 and
   1 January; it checks first that the account looks like a fresh trial and refuses otherwise.
3. **Nothing for reconciliation.** sevDesk refuses hand-made transactions on offline accounts and
   cash registers (422 "You can only create transactions on online checkaccounts", recorded
   2026-11-08). The probes and the M4 scenario therefore create **one tagged file-import bank
   account** per run (`POST /CheckAccount/Factory/fileImportAccount`, named `MCP-E2E … Import`,
   type CSV, default booking account) and enter their test transactions there. It is in the
   cleanup list; delete it in the web app at the end.
4. The booking accounts come from ReceiptGuidance (SKR04 6815 Bürobedarf with tax rule 9 at 19 %,
   4400 with rule 1, or the first account that fits), so a standard chart of accounts needs no
   setup.

## Runs, in this order

```bash
export SEVDESK_API_TOKEN_FILE=~/.config/sevdesk-trial.token
W="SEVDESK_LIVE_I_UNDERSTAND_WRITES=1"

# 1. Read-only: SevClient keys, AccountDatev paging, CSV exports, transaction log.
pnpm probe --only read-sevclient-keys,read-account-datev-paging,read-export-csv,read-transaction-log,read-voucher-pos-account-datev \
  --out probe-report-m4-read.md

# 2. Writes: vouchers (upload, save, update, delete, finalize, payments, reset), transactions on
#    the file-import account (create, split, booking types, private), the DATEV job (refused
#    without a configuration), a ZUGFeRD receipt; then the reads that now have data.
env $W pnpm probe --allow-writes --only write-voucher-upload-temp-file,write-voucher-save-with-file,write-voucher-net-gross,write-voucher-open-directly,write-voucher-update-draft,write-voucher-invalid-account-rule,write-voucher-revenue,write-voucher-delete,write-voucher-finalize,write-voucher-book-amount,write-voucher-reset,write-transaction-create,write-transaction-split-booking,write-transaction-split-variants,write-transaction-private-status,write-export-datev-csv,write-voucher-zugferd-upload,read-transaction-log,read-sevclient-keys,read-account-datev-paging,read-voucher-pos-account-datev,read-export-csv,read-voucher-document-key,read-transaction-date-filters,read-transaction-status-filter,read-update-after,read-list-defaults \
  --out probe-report-m4-write.md

# 3. Opt-in: a fake DATEV configuration, then the export job again (job id, progress, the
#    download link's host and expiry format, the ZIP's entry names).
env $W pnpm probe --allow-writes --only write-export-datev-config,write-export-datev-csv \
  --out probe-report-m4-datev.md

# 4. Opt-in, after the company data (step 1 above): one e-invoice, FINALIZED (it cannot be
#    deleted). Attaches the scrubbed getXml answer to the report as a fixture candidate; after
#    a review it goes to test/fixtures/einvoice/sevdesk/ (see the README there).
env $W pnpm probe --allow-writes --only write-einvoice-xml --out probe-report-m4-einvoice.md

# 5. Fixtures (read-only), then the live checks and the scenarios (M3 and M4).
pnpm fixtures:record
pnpm test:live
SEVDESK_LIVE_LIFECYCLE=1 SEVDESK_LIVE_I_UNDERSTAND_WRITES=1 pnpm test:live
```

Behind a filtering proxy the DATEV download also needs the S3 host that `jobDownloadInfo` names
(the probe report states it); the probe fetches the ZIP without credentials.

## What the M4 runs create and how they stay safe

- Generated files only: one-page PDFs and a 1×1 PNG with the run tag, and a minimal Factur-X PDF
  (EN 16931 CII inside). Never upload real receipts.
- Vouchers (drafts, open, paid and reset ones; the scenario deletes its own draft), transactions
  on the file-import account (status 100 again after the resets), finalized invoices for the
  booking probes, one contact, the file-import account. All tagged and in the cleanup list.
- `saveVoucher` for anything but a draft (status 50) needs the `commit` tier; the client refuses it
  otherwise. Bookings, resets and transaction status changes are `commit` as well.
- The DATEV job is a `POST` (the spec's GET answers 500 "wrong HTTP Type"), never with
  `enshrineDocuments`; the XML job is started only by the opt-in gap probe
  `write-export-datev-xml` (below). The report keeps only the download link's host and the expiry
  format; ZIP entry names have long digit runs (accountant and client numbers) masked. Neither the
  ZIP nor the link is ever written to the repository.
- CSV exports: only the header row reaches the report (the evidence keeps the first line of a
  non-JSON body), never data rows.
- `read-sevclient-keys` shows only key names, booleans, `0`/`1` flags and short codes, never names,
  addresses, IBAN or numbers.
- The e-invoice fixture candidate is scrubbed by a structure-keeping XML scrubber (element names,
  codes, amounts, dates and the BT-24 profile stay; names, addresses, contact data, bank and tax ids,
  document numbers and free text become fakes; embedded files become a placeholder) and once more
  by the report's scrubber. It has no XML declaration: add `<?xml version="1.0" encoding="UTF-8"?>`
  back when it becomes a fixture.
- The M4 scenario's local folders (`SEVDESK_FILE_DIRS` with the generated PDFs, `SEVDESK_OUTPUT_DIR`
  for the DATEV ZIP) are temporary and removed at the end.

## Gap probes: banking, exports, receipt recognition

The probes of `scripts/lib/probes/gaps-banking-probes.ts` (issues #88, #92, #95, #96; first run
2026-11-16, findings D-095 to D-103) need the M4 preparation; the opt-in cash-register probe also
needs a cash register (Kasse) with a positive balance. They run on the trial account only, like
everything on this page.

```bash
# 1. Writes that can be cleaned up, then the reads.
env $W pnpm probe --allow-writes --only write-check-account-factories,write-transaction-delete,write-private-transaction-rule,write-receipt-hash,write-export-invoice-zip,write-export-voucher-zip,read-check-account-kinds,read-transaction-soft-delete,read-document-hash \
  --out probe-report-gaps-banking.md

# 2. Opt-in, one per run, last. Each needs --only.
env $W pnpm probe --allow-writes --only write-cash-register-transaction --out probe-report-gaps-cash.md
env $W pnpm probe --allow-writes --only write-voucher-from-file --out probe-report-gaps-recognition.md
env $W pnpm probe --allow-writes --only write-export-datev-xml --out probe-report-gaps-datev-xml.md
env $W pnpm probe --allow-writes --only write-transaction-enshrine --out probe-report-gaps-enshrine.md
```

What they create and change:

- Tagged vouchers (open and draft vouchers with generated receipts), tagged transactions on the
  tagged file-import account (the delete probe's rows end soft-deleted, sevDesk only sets
  `deletedAt`, D-096; the rule probe's six stay open), a clearing account and a second file-import
  account (archived by `DELETE`, status 0, D-097), one tagged contact with a draft and a finalized
  invoice, two private-transaction rules (deleted at the end).
- The ZIP exports run with filters (a fresh contact, a date window, amounts) and `limit`, first
  with `limit` 1 and filters that match nothing; they change no document (D-101). The report keeps
  entry names only as patterns (words, digits and hashes masked), sizes and counts.
- Opt-in and irreversible: `write-cash-register-transaction` pays a tagged cash sale and a cash
  expense on the Kasse and resets both vouchers to open; the two bookings and the two
  counter-entries of the resets stay in the cash book (D-095, D-096), and the cleanup list names
  them as permanent cash-book entries. `write-transaction-enshrine` enshrines one tagged
  transaction the probe created itself, booked to a tagged voucher, which then can no longer be
  reset (D-098); `write-export-datev-xml` starts the DATEV XML job twice (it marked nothing as
  exported, D-102); `write-voucher-from-file` leaves the draft voucher sevDesk's recognition
  creates (D-103).
- Hashes are compared, never printed; the XML job's link is fetched only through the server's
  export downloader (the recorded S3 host, no redirects, no credentials).

What to commit: `banking/check-accounts.json` of `pnpm fixtures:record` (contract test
`test/contract/recorded-gaps-banking.test.ts`) and the findings in `spec/deviations.md`. An empty
`banking/private-transaction-rules.json` shows no row shape and is not kept.

## Re-checks of the one-off facts of 2026-11-16/17

Some facts in `spec/deviations.md` came from one-off checks on the trial account, not from a
probe. Four probes re-check them (#135) and answer `confirmed` when sevDesk still behaves as
recorded, `contradicted` with the difference when it does not. They need the M4 preparation,
none is opt-in, and each deletes what it made at its end, also when a step fails. The one record
that stays is the run's tagged file-import account, which the two banking probes create (or reuse
from another probe of the same run): the API can only archive it, so delete it in the web app at
the end, as in [What to prepare](#what-to-prepare). The rule probe needs an account with fewer
than 1000 rules; with more, it answers `inconclusive`.

```bash
env $W pnpm probe --allow-writes --only write-custom-field-limits,write-check-account-number-refusals,write-transaction-create-answer,write-private-transaction-rule-storage \
  --out probe-report-rechecks.md
```

- `write-custom-field-limits` (D-086): a setting name of 31 characters is refused with 400, one of
  30 is taken; a value of 100 characters is kept, a PUT of 101 is refused with 400; a second value
  for the same contact and setting is refused with 400; the search finds an organisation and a
  person and ignores `limit` and `offset`; deleting a contact and deleting a setting each delete
  the values. It makes a setting (a second one only if sevDesk takes the 31-character name), an
  organisation, a person and their values, and deletes them all.
- `write-check-account-number-refusals` (D-119): both account factories refuse the booking
  account number of the run's tagged file-import account with 422 "already used" and 3321 with
  422 "is invalid". An account a factory creates anyway is archived again at once (D-097).
- `write-transaction-create-answer` (D-071, D-096): two tagged rows on the file-import account,
  with and without a purpose; the answer is the row as one object with the keys of a GET row,
  and each DELETE answers `[null]` and only sets `deletedAt`. Both rows end soft-deleted.
- `write-private-transaction-rule-storage` (D-099, D-130): four tagged rules (`commit` tier): a
  text with outer spaces is kept as sent, a duplicate is stored as a second row, 255 characters
  are kept and 256 cut to 255. All four are deleted at the end.

Texts are compared, never printed. Record a contradiction in `spec/deviations.md` like any other
finding.
